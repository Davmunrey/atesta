# Spec: requirement register and statement of applicability

- Issues: #133, #226 (expected evidence). Requirement ids: FR-07 (human assessment), Gate A items 2-4 in `ROADMAP.md`
- Status: built (2026-11-23: every acceptance criterion is implemented and covered by the tests its test plan names)

## Problem

A Spanish supplier preparing ENS conformity has to keep, per Annex II measure, whether it applies
to their system, whether it is implemented and regularly reviewed, who did it, and the evidence
(RD 311/2022 Annex III 2.1.a). Their security officer then analyses that self-assessment and
records conclusions and corrective actions (Annex III 2.1.b). The selected measures are
formalised in a Declaración de Aplicabilidad (art. 28.2). Today they do this in spreadsheets and
consultant templates. Atesta shows the measures but cannot record any of it.

## Acceptance criteria

- [ ] An admin records the organization's **scope** for a framework: one value per selection axis
      the pack declares. For ENS that is the category (BÁSICA, MEDIA, ALTA) and the level of each
      security dimension (C, I, T, A, D: BAJO, MEDIO, ALTO). Values outside the pack's levels are
      rejected.
- [ ] For each requirement the register shows a **proposal** computed from the pack's
      `selection_basis` and `selection_rules` and the recorded scope: `applies`, `not_applicable`,
      or `undecided` when the scope does not cover the requirement's axis. The rule text (for
      example `+ R1+R2`) is shown verbatim. A proposal is never a decision.
- [ ] An admin records an **assessment** per requirement:
  - applicability (`applies` or `not_applicable`);
  - implementation (`not_implemented`, `partially_implemented` or `implemented`);
  - whether it is under regular review;
  - the customer's own person who performed it (name or role, at most 200 characters) and the date;
  - linked evidence statements of the same organization;
  - notes.

  A justification is required whenever the decision is `not_applicable` or differs from the
  proposal.
- [ ] An admin records the **assessment review**: the reviewer's name and role, the date, conclusions
      and corrective actions (at most 4,000 characters each). Atesta records it; the customer's
      own security officer is the reviewer, never Atesta.
- [ ] The **statement of applicability** export (JSON and CSV) lists every requirement with its
      decision, justification, the rule it came from and the scope it used. It carries:
  - an empty signer block for the responsable de la seguridad;
  - the catalog version;
  - the statement "Generated by Atesta from the organization's own records. Not a certification."
- [ ] Every write is append-only (the latest row is current), runs under RLS, and emits an audit
      event with scalar metadata only. Free text is customer content: stored and returned to
      members, never logged and never copied into audit metadata (rule 2).
- [ ] Recording assessments never changes a score (ADR-005): scores stay with checks and manual
      control reviews.
- [ ] Nothing is framework-specific (rule 9). The engine reads axes from `selection_basis`
      strings of the form `<axis> · <keys>` (`categoría · Todas`, `nivel · C I T A`), and any
      pack that uses that form gets the same behaviour.

## Expected evidence per requirement (issue #226)

An auditor asks for the same kinds of evidence for each measure. For ENS, CCN-STIC 808 (April
2026) proposes them per Annex II measure. People preparing an audit want that list next to the
measure, not in a 106-page PDF.

- [ ] A pack may give a requirement an optional `expected_evidence` block in its
      `attributes`: a short checklist (1 to 8 items) of what an auditor is likely to ask for. Any
      pack may use it (rule 9); nothing in the code names a framework or a guide.
- [ ] Each item is Atesta's own wording in ES and EN (at most 200 characters each) and cites
      its source: guide, edition (`YYYY-MM`), section and page. Guides are cited, never
      copied: no sentence or table of the guide is reproduced.
- [ ] The block carries a review marker: `reviewed_by` (the signer's name) and `reviewed_on`
      (the review date). New content has `reviewed_by: null` and no date: it is a candidate.
      Only the owner signs, one measure at a time; a signature sets both fields, and the schema
      rejects one without the other. Signing changes no other content.
- [ ] Each item's `page` is the guide's printed page number. In CCN-STIC 808 (2026-04) the
      printed number equals the PDF page index from the body onwards (pages 13 to 105). An item
      whose list continues on the next page cites the page where that part appears.
- [ ] The catalog schema rejects a block with no items, an item without ES or EN text, a page
      below 1, an edition that is not `YYYY-MM`, a blank reviewer, or a reviewer without a date
      (or a date without a reviewer).
- [ ] The framework detail returns the block with the requirement's guidance. The register
      and the auditor dossier show it as a disclosure under the requirement: each item with
      its reference, and a note that the list is a candidate pending review and never a
      verdict on the organization (ADR-005).
- [ ] The dossier lists a requirement that has expected evidence even when it has no
      controls yet.
- [ ] Every label exists in ES and EN.

The ENS pack fills the block for all 73 Annex II measures from the "Propuesta de evidencias"
of CCN-STIC 808, section 6.2; each reference names the subsection (6.2.1, 6.2.2.1 to 6.2.2.7,
6.2.3.1 to 6.2.3.8) and the measure. At least ten references are re-opened in the PDF before the pull
request, and the pull request lists them.

## Design notes

**Engine (`packages/core/src/atesta_core/applicability.py`, pure):** `propose(basis, rules, scope)`
parses the basis into an axis and its keys.
- An axis whose keys are `Todas` uses the scope's single value for that axis.
- An axis with dimension keys uses the highest level among the listed dimensions. The order comes
  from the order the pack's rules list them. This is a proposal for the reviewer; the selection
  itself is a human decision.
- A rule of `n.a.` proposes `not_applicable`; any other rule proposes `applies`.

**Data (compliance module, three tenant tables, append-only, RLS, ADR-012):**
- `framework_scopes` (organization_id, framework_key, axis_values JSONB, decided_by,
  decided_at);
- `requirement_assessments` (organization_id, framework_key, requirement_code, applicability,
  implementation, regularly_reviewed, justification, performed_by, performed_on,
  evidence_statement_ids UUID[], notes, recorded_by, recorded_at);
- `assessment_reviews` (organization_id, framework_key, reviewer_name, reviewer_role,
  reviewed_on, conclusions, corrective_actions, recorded_by, recorded_at).

No foreign keys to the global catalog or to users (ADR-008); requirement codes and evidence ids
are checked at write time. Evidence ids are checked through `evidence.api` (rule 8).

**API (`/api/v1/orgs/{org_id}/frameworks/{framework_key}/…`):** `GET|POST scope`,
`GET register`, `POST register/{requirement_code}`, `GET|POST assessment-reviews`,
`GET applicability` and `GET applicability.csv`. Members read and admins write.

**Audit actions:** `framework.scope_recorded`, `requirement.assessed`,
`framework.assessment_reviewed`, `framework.applicability_exported`.

## Test plan

- **Core:** proposals for category rules, dimension rules (highest level), `n.a.`, a missing scope
  and an unknown level.
- **Real Postgres:** RLS isolation between two organizations for each table; append-only grants
  (UPDATE and DELETE refused).
- **Validation:** a justification is required when it differs from the proposal; evidence from
  another organization is rejected; an unknown requirement returns 404; a non-admin write returns 403.
- **Audit:** metadata holds no free text.
- **Export:** the CSV has one row per requirement, the signer block is empty, and it carries the
  not-a-certification statement.
- **Scores:** recording an assessment leaves the latest score snapshot unchanged.
